# 参考匹配与简繁路由

## 两个独立决定

- 参考字形：只记录图里可辨的实际字符，以及简体/繁体/混合/未知证据。
- 输出字形：用户的明确选择；未知时询问“简体、繁体，还是两者都要”。图为繁体、用户要简体时，保留简体结构，将参考的笔形与比例迁移过去，不把「葉」直接映射进 U+53F6「叶」。

不要自动把 OCR 不确定字当作确定语料。没有证据的字标疑点，不补成符合自己命名的短语。不对参考图片做未经确认的整句转写来替代观察。

## 路由

1. 对话已有明确选择，直接使用，不再询问。最近修正高于默认与图片推断。
2. 只有图片而无范围要求：用具体字提出判断；证据充分可提出建议，同时确认输出范围。共形字和少数不确定字 → 未知，不默认简体。
3. 繁体不等于台湾；同一码位的字形可能因地区不同，覆盖也不等于地区正确。针对台/港分别检查合适底库与 locl。未指定时先试字，明确地区尚未验收。
4. 简繁都要：优先考虑同一字体保留两套字符，分别检查两种语料和覆盖。需要不同地区字形且单文件不能可靠满足时再拆地区配方/文件。共享设计规则，不依靠文字替换承诺完整地区适配。

## 先过视觉关，再扩大字符

- 先重现参考中确定的相同字，统一墨迹高度/前景背景并排展示；有简繁差异时另列目标简体试字，不把结构差异当笔形差异。
- 比较粗细对比、横竖倾斜、转角、末端、外张、中宫、字面比例；解释哪些已接近、哪些未解决。不要制造没有测量定义的相似度百分比。
- 用少量不同结构的目标字符建立规则，再逐批扩展。底库不匹配时选更近者或真正编辑轮廓。
- 导出文件必须和图中试字一致。报告分别列出：重新绘制的字符、变体轴调整字符、继承底库字符。几字修改不能等同全部汉字定制。
- 现有引擎仅支持编辑静态 glyf 已有码位。不能从 3 字自动完成数万字风格迁移，也不支持新增码位；需要专门设计源、部件系统或经核验的生成方法。

## 覆盖验收

简体用 common-3500/standard-8105 与必需语料分别报告；繁体先覆盖用户语料、数字标点，再按项目选定有来源的繁体字表。当前核心未内置台/港完整标准字表，不得把简体 8105 或字体总汉字数当繁体合格证明。

## 葉光案例中的可复用经验

上一版只选底库并改名，不能算参考风格定制。随后提取「葉」的轮廓做单字校准，再以允许修改的完整骨架，对全宽字形统一调整比例与有限轮廓特征，并保留确认的「葉」。这些阶段分别证明单字贴合、规则延展与字符覆盖，不能互相代替。

用户曾改变简繁选择，最终项目选择以最近明确要求为准；这些历史选择不是后续项目默认值。详见 [整套延展](full-font-styling.md)。
